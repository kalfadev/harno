# Claude Code setup {067bf7}

harno exists to cut the number of turns an agent spends. That only works if the agent reads, writes and runs everything through harno, and if the log sees what it does. Four pieces make that happen: the corpus, a first call, hooks and permissions. The hooks and their scripts are the claude-code harness (`tools/claude-code/`): `harno tool add claude-code` copies it into `.harno/tools/claude-code/`, and `harno run claude-code install` writes its hooks into `.claude/settings.json`. This repository runs exactly this setup (`CLAUDE.md`, `.claude/settings.json`, `strict: true`). The last section, **Your project, step by step**, puts the pieces in order for another project.

## Start the corpus {2653f1}

Start the corpus as **Guide: Install and start a project** says: `harno init`, mdmap installed from its repository with the preset `mdmap: { seq: ["mdmap {args}"] }`, `roots` and `ignore` in `mdmap.yml` at the root of the project, a first `harno run mdmap ls` gives every heading an id, commit the config and the ids. Commit the ids before `CLAUDE.md` names any of them: the start context below reads nodes by id.

## Start context {e7252b}

`CLAUDE.md` names the start command on its first line starting with `$ `: `harno run mdmap ls --depth 2 && harno run mdmap show <ids>`, the map down to the files of a folder and the nodes to read first (here the Working here sections Workflow, Rules and Call rules; Presets and Recipes are read when a task needs them). The agent runs that line as the first call of a session, and again after `/clear` or `/compact`: CLAUDE.md says so. Not `@`, because `@path` in CLAUDE.md is an import. The content stays in the docs and the ids never change, so nothing goes stale. No hook runs the line: Claude Code cuts the output of a hook past about 10,000 characters without a word, and a hook run is no call in the log. As a call it is logged, filtered and held to `warn.output` like any other. Every session reads the three nodes and the map, so a line added to one of them is paid for by a trim in another, and what only some tasks need lives outside them: **Recipes** for the discovery of a task that comes back.

## Hooks {331d7f}

Hooks keep what harno cannot see itself: which session a call belongs to, what the human wrote, what the agent answered, and what the agent did without harno. harno knows no harness: `hook.py <action>` of the claude-code tool reads the JSON Claude Code gives the hook, and the transcript, and writes the log of the session itself, `.harno/log/claude-code/<session>.jsonl`, beside the log of the gate (**Code map: The log**).

| action | Claude Code hook | what it logs |
|---|---|---|
| `session-start` | `SessionStart` | The start of the session; it also puts `HARNO_SESSION` into `$CLAUDE_ENV_FILE`, so every harno call knows its session. Without it the calls of a day log to the session `manual-<date>` and the first one says so in a warning. |
| `prompt` | `UserPromptSubmit` | What the human wrote. |
| `tool` | `PostToolUse` | Every tool call the agent made, exactly as made (`Read`, `Grep`, `Edit`, any `Bash` command, one that runs harno too, MCP), or a subagent task with its answer; before it the calls that failed since the last one, from the transcript; each with its API turn and what the agent wrote in it. |
| `response` | `Stop` | What the agent answered, and the API turns it took. |
| `session-end` | `SessionEnd` | The end of the session and why it ended. |

`install.py` writes these hooks and no other: the start context is a call of the agent (**Start context**); it writes the sandbox block too when `tool.yml` says `sandbox: true` (`sandbox.py`, **Permissions**). None of it happens on its own: `harno tool add claude-code` only copies the files, and `harno run claude-code install` is what wires them, run by the human outside the sandbox. A hook attached to the wrong event is refused. A hook prints nothing, does nothing outside a harno project, and when it refuses it exits 1, never 2: Claude Code reads 2 from `UserPromptSubmit` as "block this prompt". `harno init` does not touch `.claude/settings.json`, and neither does `harno tool remove claude-code`, which only deletes the folder: `harno run claude-code remove` is what takes the hooks and the sandbox block out again, before the folder goes. `tool.yml` comes with `strict: true`, `sandbox: true` and in `deny_tools` the tools of Claude Code that work around harno: every project that ran the harness set them so (owner, 2026-10-02).

## Permissions {6d9676}

The rules ask; permissions make sure. With `strict: true` in `.harno/tools/claude-code/tool.yml` and `harno run claude-code install` run again, the harness adds a `PreToolUse` hook on Bash and allows `Bash(harno:*)`. Bash itself cannot be denied, since harno runs through it, so the hook (`only-harno.py`, cases in `tests/test_only_harno.py`) parses each command line with `shfmt --to-json` and refuses any line that runs anything but harno: `;`, `|`, `&&` to another program, `$(…)`, backticks, `$VAR`, heredocs, variable assignments, subshells, redirection other than `2>&1` and `>/dev/null`. The hook answers the question too: a line it lets through is returned as a `permissionDecision` of `allow`, so it runs without a question. The pattern alone would not do it, since Claude Code holds a command line back from a pattern when its text is long, many-lined or looks like code — which every `implement` plan and every doc body is — so a pattern and a hook that only kept quiet left a question on nearly every call. The owner decided that the allow covers `harno run --raw` as well, so the one verb that runs a command outside `run.allow` runs unasked too: what stops it is the sandbox, which writes nowhere but the project and the three tool directories, and what keeps it is the log, where the command and its `--why` stay. Without `shfmt` the hook refuses every line, and so it does for a line it cannot read at all: every exit but 2 would let the call through. The way out stays inside harno and is logged: `harno run --raw "<command>" --why "<reason>"`. Commands go through `harno run`, which checks `run.allow`, logs each one, and chains or parallelises them in one turn. The tools of Claude Code this repository refuses are `deny_tools` in `tool.yml`, which `install.py` adds to `permissions.deny`; the list only grows, so a deny written by hand stays. Everything that reads, writes, searches, fetches, starts an agent or sends something outside the log is there; `tool.yml` holds the list. What a denied tool gave is a preset instead: context7 is `context7-search` and `context7` (**Presets**). A moved hook script blocks every Bash call until `settings.json` names its new path: move it and run `claude-code install` in one call.

With `sandbox: true` the harness writes a `sandbox` block into `.claude/settings.json` as well (`sandbox.py`, cases in `tests/test_sandbox.py`). Every Bash call then runs in the Claude Code sandbox, which writes inside the project and in the paths of `sandbox_write` (`~/.cargo`, `~/.rustup`, `~/.serena`: the state of tools that keep it outside the project) and nowhere else, and asks nothing for a sandboxed command (`autoAllowBashIfSandboxed`). Nothing takes a command out of it either (`allowUnsandboxedCommands: false`), which is what the hook allow and the silent sandbox make necessary: a `dangerouslyDisableSandbox` call would run unasked. No unix socket is open for the same reason, since a socket reaches a daemon outside the sandbox, while the 127.0.0.1 the analytics page and its tests need is `allowLocalBinding`. `sandbox_read` closes the home to reads and names what stays readable there: the programs the presets run from it (`~/.nvm` for node, `~/.local` for graphify, `~/.cargo`), `~/.gitconfig`, and `~/.claude/projects`, which the `transcript` preset reads; empty, the whole home is readable. `failIfUnavailable` ends the session when the sandbox cannot start, instead of running the calls without one. A read or a write anywhere else is refused, and the way out is one command run outside the sandbox, which the human allows. Two things follow. The sandbox never writes `.claude/settings.json`, so a change to `strict`, `deny_tools`, `sandbox_write` or `sandbox_read` reaches it only when the human runs `harno run claude-code install` outside the sandbox; inside one the write is refused. The sandbox reads no `/dev/fd`, so a check writes its lists to files under `target/` instead of a process substitution (the `areas` preset), which would fail while reporting success.
The owner turned `run.sandbox` off in this repository, `enabled: false` in `.harno/config.yml`. Both sandboxes guard the same calls and the one of the harness is the narrower: it closes the home against `sandbox_read`, where `run.sandbox` reads every path, and it cannot be left, since nothing takes a command out of it. macOS refuses a sandbox inside a sandbox, so with it on every call ends with `note: run.sandbox steps aside, an outer sandbox holds this process — sandbox-exec: sandbox_apply: Operation not permitted`: a line more on every call, and nothing gained. A project whose harness does not sandbox its agent turns it on.

## Your project, step by step {cf33a3}

For a Claude Code user who adds harno to their own project. The sections above say why each piece exists; this is the order to put them in. Steps 1 to 3 are enough to use harno and see every session in the log; step 4 keeps Claude Code inside harno.

1. **Install and start the corpus.** Install harno and mdmap with their installers (**Guide: Install and start a project**); then in the project `harno init`, the preset `mdmap: { seq: ["mdmap {args}"] }`, `roots` and `ignore` in `mdmap.yml` at the root, a first `harno run mdmap ls`, commit (**Guide: Install and start a project**).
2. **The harness.** `harno tool add claude-code` copies the hook scripts into `.harno/tools/claude-code/` and writes their presets into the config, among them `claude-code: { seq: ["python3 .harno/tools/claude-code/install.py {args}"] }`. Say in the `config` block of `tool.yml` what it should write, and run `harno run claude-code install`: the hooks go into `.claude/settings.json` beside the hooks already there (**Hooks**), with the permissions and the sandbox block the config asks for. It needs `python3`, and a sandboxed session cannot write that file, so run it outside one. Start a new Claude Code session after it.
3. **Tell the agent.** `CLAUDE.md` at the project root: a line that says to read and write the docs only through harno (`harno help` and `harno run mdmap help` list the verbs), and the start line, `$ harno run mdmap ls && harno run mdmap show <ids>`, which the agent runs as its first call, with the ids of the nodes every session needs, such as the current state, the rules and how to work. Pick them from `harno run mdmap ls`, and keep their output small, since every session reads it (**Start context**).
4. **Only harno (optional, strict).** `strict: true` in `tool.yml`, then `harno run claude-code install` again (**Permissions**). The hook needs `shfmt` (`brew install shfmt`); without it every Bash call is refused. Then list in `run.allow` every command the agent needs (build, test, git, search) and in `run.presets` the frequent ones; each command left out costs a `harno run --raw "<command>" --why "<reason>"` call. Take this step only for a project that works fully through harno: it blocks every other tool.

Check it works: start `claude` in the project. The first call of the agent is the `$` line. After a task, `harno run analytics` opens a local page with the session on it, and `harno log ls` and `harno run session` print the two logs in short lines. `warning: no session hook` on the harno calls of the agent means `session-start` is missing.
